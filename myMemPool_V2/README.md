# myMemPool

一个使用 C++20 实现的并发内存池学习项目。项目采用 `ThreadCache → CentralCache → PageCache` 三级结构，目标是理解小对象分配、自由链表、线程本地缓存、批量交换、Span 管理、相邻页合并以及并发条件下性能与内存占用之间的权衡。

当前版本已经完成基本分配与释放流程、线程本地缓存、动态高水位、按逻辑时钟缩容、Span 跟踪、空闲 Span 回收合并，以及正确性和性能测试。它适合学习和继续迭代，目前不定位为生产级通用分配器。

## 整体结构

```mermaid
flowchart LR
    A[调用者] -->|allocate / deallocate| T[ThreadCache<br/>每线程独立]
    T -->|批量获取 / 归还| C[CentralCache<br/>按大小类别组织]
    C -->|申请 / 归还 Span| P[PageCache<br/>按页管理]
    P -->|申请系统内存| S[operator new]
```

三级缓存分别承担不同职责：

- **ThreadCache**：每个线程独享，命中时只操作本地自由链表，不需要加锁。
- **CentralCache**：在线程缓存之间周转内存块，以大小类别为单位维护中心自由链表。
- **PageCache**：以页和 Span 为单位管理大块内存，负责切分、回收和合并相邻空闲 Span。

## 主要参数

| 参数 | 当前值 | 含义 |
| --- | ---: | --- |
| `ALIGNMENT` | 8 B | 小对象按 8 字节对齐并划分类别 |
| `MAX_BYTES` | 256 KB | 不超过该值的申请进入内存池 |
| `FREE_LIST_SIZE` | 32768 | 当前大小类别数量 |
| `PAGE_SIZE` | 4096 B | PageCache 的逻辑页大小 |
| `SPAN_PAGES` | 8 | CentralCache 缺少内存时最少申请 8 页 |
| 中心批量目标 | 16 KB | 每次从 CentralCache 获取的目标总字节数 |
| 中心批量范围 | 4～256 块 | 根据块大小动态计算 |
| 单次归还上限 | 512 块 | 限制一次持有中心锁的时间 |

大于 256 KB 的申请绕过内存池，直接使用 `operator new` 和 `operator delete`。

## 大小类别

当前版本从 8 字节到 256 KB 始终以 8 字节为间隔划分类别：

```text
index = ceil(size / 8) - 1
blockSize = (index + 1) * 8
```

这种映射简单，而且内部碎片较小，但会产生 32768 个类别，使每个 ThreadCache 包含较大的元数据数组。后续计划改为分段粒度：小对象保持细粒度，大对象逐步使用 16、32、128、1024 字节等更大的间隔。

## 分配流程

### 小对象

1. 根据申请大小计算 `index`。
2. 如果当前线程的 `freeList_[index]` 非空，摘下链表头并直接返回。
3. 如果线程本地链表为空，向 CentralCache 批量获取一组内存块。
4. 第一块返回调用者，其余块挂入当前线程的自由链表。
5. 如果 CentralCache 对应类别为空，则向 PageCache 申请一个 Span，并切分成等大的内存块。

自由块本身的前几个字节用于保存下一节点指针，因此不需要为每个小块单独分配链表节点。

### 大对象

当 `size > MAX_BYTES` 时，直接调用系统 `operator new`。释放时必须传回相同的大小，才能选择正确的释放路径和大小类别。

## 释放流程

1. 根据大小计算 `index`。
2. 将内存块插入当前线程自由链表的头部。
3. 当链表长度超过动态高水位时，提高该类别的水位上限，并向 CentralCache 归还一部分内存。
4. 每次最多归还 512 块，减少单次占用中心锁的时间。
5. CentralCache 更新对应 Span 的空闲块计数。
6. 当一个 Span 中的所有块都空闲时，将属于该 Span 的块从中心自由链表摘除，并把整个 Span 交还 PageCache。
7. PageCache 尝试与左右相邻的空闲 Span 合并，减少外部碎片。

线程退出时，ThreadCache 析构函数会把仍保留的自由链表归还 CentralCache。

## ThreadCache 的动态水位和缩容

每个大小类别都有独立的 `maxListSize_`。初始值由类别大小计算，当前公式对应每个类别约 256 KB 的初始缓存容量。

当释放后的链表长度超过上限时：

1. 将该类别的上限翻倍；
2. 从线程本地链表尾部切出一批节点；
3. 最多向 CentralCache 归还 512 块。

扩容后，经历过较大分配峰值的线程可以在后续循环中主要命中本地链表，减少对 CentralCache 锁的竞争。

为避免所有历史峰值永久叠加，当前版本使用分配次数作为逻辑时钟：

- `allocate` 更新总操作序号和当前类别的最近活动序号；
- 只登记线程实际使用过的大小类别；
- 每约 `2^21` 次分配检查一次这些类别；
- 如果某类别在逻辑时间内长期没有活动，并且上限高于初始值，就将上限减半；
- 若当前空闲块仍超过新上限，则逐步归还 CentralCache。

这是一种明确的性能与内存折中。它避免完全不回收的高水位策略，但会给热点路径增加计数、状态记录和缩容 bookkeeping。当前测试中，这部分成本对多线程吞吐有可见影响。

## CentralCache

CentralCache 为每个大小类别维护一条中心自由链表，并使用独立的 `atomic_flag` 自旋锁保护同一类别的批量获取和归还。

批量大小以约 16 KB 为目标，并限制在 4～256 块之间。小块一次获取更多，大块一次获取更少。

`SpanTracker` 记录：

- Span 起始地址；
- 页数；
- 总块数；
- 当前空闲块数；
- 对应的 PageCache Span。

Tracker 使用以 Span 首地址为键的有序映射保存。给定任意块地址时，通过 `upper_bound` 找到可能所属的 Span，并检查地址是否位于该 Span 的半开区间内。

当 Tracker 的空闲数等于总块数时，CentralCache 会清除该 Span 的所有中心空闲块并把 Span 归还 PageCache。

## PageCache

PageCache 以页为单位管理 Span：

- `spanMap_` 按起始地址保存 Span，用于查找相邻区域；
- `freeSpans_` 按页数保存空闲 Span 链表；
- 申请时使用 `lower_bound` 查找页数足够的空闲 Span；
- 如果找到的 Span 更大，就切分并把剩余部分重新放回空闲结构；
- 释放时同时检查左右相邻 Span，只有确认相邻 Span 位于空闲结构中才进行合并。

当前底层通过 `operator new(numPages * PAGE_SIZE)` 获取系统内存。空闲 Span 会保留在 PageCache 中供后续复用，尚未实现把大块空闲区域真正归还操作系统。

## 并发设计

- ThreadCache 为 `thread_local` 对象，常见命中路径不加锁。
- CentralCache 为每个大小类别提供一把自旋锁，不同类别可以并行操作。
- Span Tracker 使用独立互斥锁保护有序映射。
- PageCache 使用一把互斥锁保护 Span 映射、空闲 Span 和切分合并过程。
- 自由链表的节点存储在空闲块内部，减少额外元数据分配。

同一大小类别被大量线程同时访问时，CentralCache 的类别锁仍可能成为瓶颈。动态水位通过提高ThreadCache命中率来减少进入中心层的次数。

## 构建与运行

### 环境

- Visual Studio 2022
- MSVC v143
- C++20
- Windows x64

### Visual Studio

1. 打开 `MEM.sln`。
2. 配置选择 `Release` 和 `x64`。
3. 使用 **Ctrl+F5** 执行，避免附加调试器干扰性能数据。

正式模式无需命令行参数。快速验证可在“项目属性 → 调试 → 命令参数”中填写：

```text
--quick
```

性能数据应以 Release 模式为准。Debug 模式包含额外检查和未优化代码，不适合与系统分配器比较。

## Benchmark

`benchmark.cpp` 包含以下测试：

- 基本正确性：检查非空返回、活动地址不重复和释放后的复用；
- 单线程固定大小：反复申请和释放 64 字节块；
- 单线程混合大小：覆盖 8～2048 字节的 12 种大小；
- 并行固定大小：使用 `hardware_concurrency()` 个线程同时申请和释放 64 字节块；
- 对照组：使用全局 `operator new` 和 `operator delete` 执行相同工作负载。

正式模式每个样本运行 64 轮，重复 5 个样本，交替执行内存池和系统分配器，最后报告中位数与范围。测试会实际写入申请的内存，避免只测量未使用的地址分配。

当前并行计时包含 ThreadCache 的构造和析构，因为计时在启动工作线程后开始，并在线程 `join` 完成后结束。因此结果同时反映：

- 线程本地缓存初始化；
- 正常分配与释放；
- 线程退出时的集中归还。

若要单独研究稳态吞吐，应增加另一组测试：在计时前完成线程缓存初始化，在工作完成后先记录结束时间，再允许线程退出。

## 当前性能结论

在当前开发机器和现有benchmark下：

- 单线程固定与混合场景能够明显优于系统 `operator new`；
- 动态高水位显著减少了 ThreadCache 与 CentralCache 的往返；
- 加入逻辑时钟和缩容记录后，多线程测试目前约比系统实现慢 50%；
- 这部分差距体现了主动回收、线程缓存元数据、热点路径 bookkeeping 和线程退出归还的成本。

结果与CPU、Windows堆实现、编译选项、线程数量和工作负载高度相关，不应把单次数字当作通用结论。本项目选择保留缩容能力，而不是为了固定benchmark无限保留所有历史峰值。

## 已知限制

- 32768个大小类别使每个ThreadCache包含较大的数组，增加构造、析构和缓存压力。
- `allocate` 的逻辑时钟与活动记录位于热点路径，会影响极限吞吐。
- 动态水位使用倍增和减半策略，仍可能在阶段性工作负载下产生扩缩容振荡。
- CentralCache 同一类别只有一把自旋锁，高并发固定大小场景仍会竞争。
- Tracker 使用 `std::map`，批量操作中包含地址查询和全局Tracker互斥锁。
- PageCache 尚未把长期空闲的系统内存交还操作系统。
- API 要求调用者在 `deallocate` 时提供与申请相符的大小，目前没有在块头保存大小信息。
- 当前正确性测试主要覆盖64字节对象，尚缺少跨类别、边界大小、随机序列和高并发压力测试。
- `newElement` / `delElement` 模板辅助接口仍属于实验代码，尚未整理为稳定的头文件API。

## 下一步优化方向

### 1. 分段大小类别

将统一8字节粒度改为分段粒度，例如：

- 小对象保持8或16字节间隔；
- 中等对象使用32、64或128字节间隔；
- 大对象使用1KB或更大的间隔。

目标是在可接受的内部碎片下，把类别数量从32768压缩到几百个，减少ThreadCache元数据、初始化、析构和扫描成本。

### 2. 更低成本的缩容策略

- 将逻辑时钟采样移出每次分配的热点路径；
- 使用扫描轮次而不是完整操作序号；
- 限制每轮缩容和归还数量；
- 记录一段时间内自由链表的低水位，只归还真正长期未使用的部分；
- 增加每线程总缓存预算，而不只是每个类别独立控制。

### 3. CentralCache 并发优化

- 比较自旋锁与 `std::mutex` 在高竞争下的表现；
- 对热点类别进行分片，减少所有线程竞争同一链表；
- 调整批量大小，使锁次数、内存占用和局部性之间取得更好平衡；
- 缩短持有类别锁和Tracker锁的时间。

### 4. Span 元数据优化

- 减少批量操作中的逐块 `std::map` 查询；
- 研究页号到Span的直接映射或更紧凑的页级索引；
- 简化当前原子字段与外层互斥锁重复提供同步的部分。

### 5. PageCache 与系统内存

- 为超大空闲Span增加归还操作系统的策略；
- 区分保留页和可释放页；
- 继续验证左右合并、连续多Span合并和映射更新的正确性；
- 研究 Windows 虚拟内存接口或跨平台页分配接口。

### 6. 测试与观测

- 增加并行混合大小测试；
- 增加不同线程使用不同类别的测试；
- 增加突发、空闲、再次突发的阶段性负载；
- 统计 CentralCache 获取/归还次数、锁等待次数、PageCache 系统申请次数和峰值缓存字节数；
- 使用 AddressSanitizer、并发压力测试和更大规模的正确性验证；
- 分开报告稳态吞吐与线程完整生命周期成本。

## 项目总结

这个项目的重点不仅是让自由链表比 `operator new` 更快，而是完整走通一个并发内存池的关键问题：

- 为什么需要线程本地缓存；
- 为什么要批量交换内存；
- 如何跟踪一个块属于哪个 Span；
- 什么时候可以安全回收整个 Span；
- 为什么空闲 Span 需要合并；
- 如何在吞吐、锁竞争、碎片和内存驻留之间做取舍；
- 为什么benchmark中的最快策略不一定是工程上最合适的策略。
